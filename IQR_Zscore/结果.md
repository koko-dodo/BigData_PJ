## 2. 从 Baseline 到 IQR + Z-score 说明什么

### 2.1 V1 Baseline 的意义

`IQR_baseline` 是第一版可解释的无监督异常检测方法。它说明：

```text
在没有可靠标签的情况下，可以先用分位数统计规则从大规模监控数据中识别异常点。
```

V1 的整体结果为：

```text
总数据量：44,972,147
IQR 异常点：574,873
异常率：约 1.28%
```

这说明 IQR 能作为一个可运行、可解释的基础方案。

### 2.2 为什么要加入 Z-score

IQR 的判断依据是：

```text
value 是否超出 Q1 / Q3 扩展得到的上下界
```

也就是说，IQR 主要从分位数角度判断异常。但有些点虽然超出了 IQR 边界，相对于该指标整体均值和标准差来看，未必是特别极端的异常。

Z-score 从另一个角度判断异常：

```text
这个点距离均值有多少个标准差
```

两者关注点不同：

```text
IQR：看是否超出分位数范围
Z-score：看是否明显偏离均值
```

因此 V2 采用严格策略：

```text
is_anomaly_final = is_anomaly_iqr AND is_anomaly_zscore
```

含义是：

```text
一个点不仅要超出 IQR 正常范围，还要明显偏离该序列均值，才作为最终异常点。
```

### 2.3 为什么要这么做

从 V1 到 V2 的目的不是简单叠加算法，而是形成一个清晰的迭代逻辑：

```text
先用 IQR 建立 baseline；
发现单一 IQR 可能包含较多低置信异常点；
于是加入 Z-score 进行二次确认；
最终得到更保守、更聚焦的高置信异常集合。
```

本次实验结果也验证了这一点：

```text
IQR Baseline 异常点：574,873
IQR + Z-score 最终异常点：129,228
异常率从约 1.28% 降低到约 0.287%
```

这说明 V2 过滤掉了大量只被 IQR 单一规则判异常的点，保留的是同时被两种统计规则认可的异常点。

报告中可以这样表述：

```text
IQR Baseline 提供了一个简单、无监督、可解释的异常检测基线。但实验发现，单独使用 IQR 会检测出较多异常点，其中一部分可能只是超出分位数边界的正常波动。为提高异常判定的置信度，第二版引入 Z-score，从均值和标准差角度进一步判断异常程度。最终采用 IQR AND Z-score 的严格策略，只保留同时满足两种统计规则的点。实验结果显示，异常点从 574,873 个减少到 129,228 个，异常率从约 1.28% 降至约 0.287%，说明该方法有效过滤了低置信异常，使检测结果更加聚焦。
```

## 4. 五类汇总结果

### 4.1 全量统计

读取五类 V2 最终异常点：

```scala
val anomalyBase = "hdfs://master:9000/aiops/output/iqr_zscore_fast/anomaly_points"

val anomalies = spark.read.parquet(
  anomalyBase + "/service",
  anomalyBase + "/node",
  anomalyBase + "/jvm",
  anomalyBase + "/istio",
  anomalyBase + "/container"
)
```

统计总数据量和 V2 最终异常点数：

```scala
val clean = spark.read.parquet("hdfs://master:9000/aiops/output/clean_metrics")

val total = clean.count()
val anomaly = anomalies.count()

println("Total = " + total)
println("Anomaly = " + anomaly)
println("Rate = " + anomaly.toDouble / total)
println("Rate(%) = " + anomaly.toDouble * 100 / total)
```

结果：

| 指标 | 数值 |
|---|---:|
| Total | 44,972,147 |
| V2 Final Anomaly | 129,228 |
| Rate | 0.0028735119 |
| Rate(%) | 0.2873511909% |

按 `metric_type` 汇总：

统计命令：

```scala
anomalies
  .groupBy("metric_type")
  .agg(
    count("*").alias("final_anomaly_count"),
    countDistinct("object_id", "kpi_name").alias("final_anomaly_series_count")
  )
  .orderBy("metric_type")
  .show(false)
```

结果：

| metric_type | final_anomaly_count | final_anomaly_series_count |
|---|---:|---:|
| container | 40,554 | 1,242 |
| istio | 64,184 | 646 |
| jvm | 12,710 | 86 |
| node | 11,144 | 146 |
| service | 636 | 15 |

校验：

```text
40,554 + 64,184 + 12,710 + 11,144 + 636 = 129,228
```

对比 V1：

| 版本 | 异常点数 | 异常率 |
|---|---:|---:|
| V1 IQR Baseline | 574,873 | 约 1.28% |
| V2 IQR + Z-score | 129,228 | 约 0.287% |

结论：

```text
V2 使用 IQR AND Z-score 严格策略后，最终异常点数从 V1 的 574,873 个减少到 129,228 个；
总体异常率从约 1.28% 降低到约 0.287%；
说明 V2 明显收紧了异常判定条件，保留的是同时满足两种统计规则的高置信异常点。
```

按类型对比 V1 与 V2：

统计命令：

```scala
val v1s = v1.groupBy("metric_type")
  .agg(count("*").alias("v1_iqr_anomaly_count"))

val v2s = anomalies.groupBy("metric_type")
  .agg(count("*").alias("v2_final_anomaly_count"))

v1s.join(v2s, Seq("metric_type"))
  .withColumn(
    "reduced_count",
    col("v1_iqr_anomaly_count") - col("v2_final_anomaly_count")
  )
  .withColumn(
    "v2_over_v1_rate",
    col("v2_final_anomaly_count").cast("double") / col("v1_iqr_anomaly_count")
  )
  .orderBy("metric_type")
  .show(false)
```

结果：

| metric_type | v1_iqr_anomaly_count | v2_final_anomaly_count | reduced_count | v2_over_v1_rate |
|---|---:|---:|---:|---:|
| container | 238,853 | 40,554 | 198,299 | 0.1697864377 |
| istio | 167,447 | 64,184 | 103,263 | 0.3833093456 |
| jvm | 85,374 | 12,710 | 72,664 | 0.1488743646 |
| node | 73,792 | 11,144 | 62,648 | 0.1510190807 |
| service | 9,407 | 636 | 8,771 | 0.0676092272 |

进一步解释：

```text
service 的保留比例最低，V2 仅保留 V1 异常点的约 6.76%；
istio 的保留比例最高，V2 保留 V1 异常点的约 38.33%；
container、jvm、node 的保留比例约在 14.89% 到 16.98% 之间。
```

这说明不同类型指标中，IQR 异常点与 Z-score 异常点的重合程度不同。`istio` 中有更多 IQR 异常同时也明显偏离均值，因此在严格策略下保留比例更高；`service` 中许多 IQR 异常没有达到 Z-score 阈值，因此被 V2 过滤掉。
